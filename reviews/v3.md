## Блокирующие замечания

P1 — исправить до пилота с рабочими обязательствами. У каждого пункта ниже есть воспроизведение; проверки с управляемой моделью доказывают поведение кода при заданном ответе, а не частоту галлюцинаций.

### G01 · P1 · Разрешённая операция срока по-прежнему определяется неверно

**Код:** `src/flowci/formatting.py:48`, `:60`, `:345`, `:368`; `src/flowci/agent.py:615`, `:622`, `:1929`.

Точный пример v2 с «Дедлайн не меняй» исправлен. Но живой прогон подтвердил три соседних отказа:

1. **Дата измерения становится сроком.** У карточки дедлайн 25.11.2026. Сообщение «Дополни …: **срок обработки сократился с 4 до 2 секунд; измерено 2026-11-02**» записало дедлайн **02.11.2026**. Перенос не запрашивался. Regex считает слова `срок`, `к`, `до` достаточным признаком операции и ищет дату в соседнем окне. Изолированно то же произошло от «результат **к** публикации. Измерение 2026-11-01».
2. **Явный перенос выбирает старую дату.** «Перенеси срок задачи с **2026-11-25 на 2026-12-01**» завершился успешным ответом, но срок остался **25.11**. Код выбирает первую дату и заменяет корректную целевую дату из ответа модели.
3. **Вопрос самого бота обнуляет дату человека.** В трёхходовом диалоге вопрос содержал «какой срок **или срока нет**?». Человек ответил `до 2026-11-23`, настоящая модель вернула `due_date=2026-11-23`, `no_deadline=false`. В Vikunja создана карточка **без срока**. `_dialog_prompt` включает процитированный вопрос, `_NO_DEADLINE` принимает фразу агента за волю человека, `_enforce` заменяет дату на null. Название, ожидаемый результат и следующий шаг при этом сохранились — прежняя потеря постановки исправлена.

Есть и детерминированный policy-probe: при отсутствии просьбы переносить срок модельное `due_date="завтра"` всё ещё проходит через `_coerce_due_word`.

**Нужно:** отделить человеческое намерение от текста вопросов и цитат; применять типизированную операцию `keep/set/clear` с целевой датой. Извлечение даты из всего диалога или по отдельному предлогу не является проверкой разрешения.

### G02 · P1 · Второе ожидающее событие наследует контекст и evidence первого

**Код:** `src/flowci/agent.py:482`; `src/flowci/store.py:486`.

После двух Cursor-событий A и B canonical dialog `event:B` получил `original_text`, facts, task_hint и `extra.deduplication_key` **от A**. Новый B не имеет собственного canonical dialog, `_finalize` подхватывает общий dialog `cursor`; `save_dialog` затем сохраняет прежние original/source/extra без проверки совпадения event ID.

Это влияет и на права: A имел существующий файл, B — `artifacts=[]`. После короткого ответа на вопрос B только «Это задача #1» управляемая decision с `confirmed_result` была принята благодаря **чужому файлу A**. В карточку записан `B_UNVERIFIED_RESULT_WITHOUT_B_FILE`.

Это доказанный обход проверки при заданном ответе модели, а не live галлюцинация. Прямой одиночный сценарий R03 из v2 теперь защищён; ошибка возникает при нескольких ожидающих событиях.

**Нужно:** неизменяемый контекст хранить по идентификатору конкретного события/диалога. Общий ключ источника не может передавать original, разрешения и артефакты новому event ID. Проверять принадлежность evidence непосредственно перед записью результата.

### G03 · P1 · Ответ на завершённый вопрос выполняет другое ожидающее событие

**Код:** `src/flowci/agent.py:704`.

Прямой reply на A, когда A и B ещё ожидают, исправлен. Но после успешного ответа на A его привязка исчезает. Если пользователь снова отвечает на старое сообщение A, `find_dialog_by_message` ничего не находит, а fallback выбирает единственное оставшееся событие **B**.

В проверке через настоящий Dispatcher повторный `reply_to_message_id` старого A создал **Delta B**. Ответ явно адресовался другому вопросу.

**Нужно:** явный reply на неизвестный/завершённый вопрос не должен выбирать другое событие. Сохранить завершённую привязку либо вернуть понятный статус/уточнение. Автоматический fallback допустим только при отсутствии явной адресации.

### G04 · P1 · Восстановление создания выбирает чужую карточку по префиксу маркера

**Код:** `src/flowci/vikunja.py:149`, `:167`; `src/flowci/agent.py:799`.

Поиск использует `if marker in description`. Поэтому `flowci-event:…-1` совпадает с `flowci-event:…-10`.

На настоящей тестовой Vikunja создана собственная карточка с маркером `own-v3-marker-10`. Для другого события `own-v3-marker-1` намеренно введён transport failure **до отправки нового PUT**. Клиент нашёл прежнюю карточку по подстроке, ответил `create ok=True` и добавил в неё комментарий нового события. Новый event стал `done`; нужная новая карточка не создана. Собственная seed-карточка после проверки удалена.

**Нужно:** точная идентичность маркера с границами значения либо отдельное устойчивое соответствие event ID ↔ task ID. При неоднозначности восстановление должно остановиться, а не менять первую найденную карточку. Проверить также fallback агентского поиска.

### G05 · P1 · Lease события истекает, пока первый исполнитель ещё работает

**Код:** `src/flowci/store.py:14`, `:321`, `:385`; `src/flowci/agent.py:349`.

Короткая параллельная доставка исправлена: в живом контроле создана одна карточка, модель вызвана один раз. Но lease фиксирован на 120 секунд, без продления и fencing. Если первый LLM-вызов продолжается дольше, повтор забирает lease; прежний исполнитель не узнаёт о потере владения и также создаёт карточку.

В изолированном probe часы сдвинуты на **121 секунду** при ещё ожидающей первой модели: получены **две карточки, два model calls**. Это ускоренная симуляция длительного запроса, не живой двухминутный сетевой прогон.

**Нужно:** продление владения и проверка актуального owner/generation перед внешней записью; альтернативно — ограничение времени операции, которое гарантированно короче lease, с безопасной отменой старого исполнителя. Одного времени истечения недостаточно для защиты от активного старого владельца.

### G06 · P1 · Busy-ответ подтверждает доставку, хотя обработка затем может завершиться ошибкой

**Код:** `src/flowci/agent.py:329`, `src/flowci/ingest.py:99`, `.cursor/hooks/task-sync.py:148`, `:228`.

Busy возвращается как `ok=true`, `noop=true`, `already processing`. Hook принимает такой ответ за успешную доставку и удаляет файл outbox. Если первая активная обработка после этого падает, event остаётся `claimed`, карточки нет, а автоматического повтора уже нет.

В probe настоящие hook и aiohttp ingest обработали повтор из заранее подготовленного outbox во время удержанного model call. Ответ busy удалил очередь **1 → 0**; затем исходная модель вернула ошибку, итог — **0 карточек**, event `claimed`. Сам начальный пятисекундный HTTP timeout не воспроизводился: outbox явно подготовлен как состояние после неуспешной доставки.

Исходный payload остаётся в SQLite; утверждать его физическую потерю неверно. Теряется автоматическое продолжение: scheduler не подбирает такие `claimed` события, а новая session note может уже содержать другое событие.

**Нужно:** согласовать семантику «принято в надёжную очередь» и «выполнено». Если сервер подтверждает владение событием, он должен самостоятельно довести его до результата/явной ошибки с retry. Иначе hook должен сохранять повтор, пока обработка не завершена.

## Решение перед пилотом

**Рабочие обязательства пока не стоит доверять этой версии без ручной сверки.** Нужны программные исправления G01–G06, затем живой Telegram и настоящий Cursor stop. Успех последних двух проверок не компенсирует уже воспроизведённые изменения неверной карточки или срока.

Рекомендованный порядок:

1. Отделить поля человеческого намерения от вопросов/цитат; применять явную операцию срока с целевой датой.
2. Изолировать контекст и evidence по event ID; сделать явный reply строгой привязкой, включая завершённые вопросы.
3. Сделать точное восстановление идентичности event/task и единое владение полным исполнением, а не отдельными стадиями.
4. Согласовать ack hook/ingest с серверным retry; добавить renewal/fencing и recovery executing-подтверждений.
5. Повторить проверки с двумя независимыми событиями, истечением lease и отказом после busy; затем пройти внешние Telegram/Cursor пути.

Новая замена harness для этих исправлений не требуется: обнаруженные ошибки находятся в правилах применения и хранении состояния. Поиск старых заметок и приоритеты можно оставить за рамками, как согласовано.

## Как воспроизвести

Из `C:\projects\flowci`:

```powershell
$env:PYTHONPATH = 'src'
$env:PYTHONIOENCODING = 'utf-8'
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe reviews/v3-evidence/product_probe.py
.\.venv\Scripts\python.exe reviews/v3-evidence/channels_probe.py
.\.venv\Scripts\python.exe reviews/v3-evidence/integrity_probe.py
```

Эти диагностические probes используют временные данные; exit 0 означает завершённую проверку, включая найденные нарушения ожиданий. Исторические скрипты v1/v2 не запускались, чтобы не перезаписывать архив.

`live_probe.py` самостоятельно поднимает/останавливает отдельную Vikunja на 3457 и вызывает настроенный RouterAI; повторный запуск расходует API-вызовы. `live_marker.py` требует уже работающий **тестовый** fixture от этого скрипта и удаляет только собственную seed-карточку. Для STT читается сохранённая синтетическая запись, пользовательское аудио не использовалось. Рабочий порт 3456 в скриптах для тестовых операций не применяется.

Полный Telegram-клиент, реальный Cursor stop, многодневная эксплуатация, нагрузочное тестирование и чистая установка на другой машине в этой итерации не проверены.
